> 임시 게시글: 작업 기록을 바탕으로 작성한 초안이며, 이후 다듬을 예정이다.

> 업무에서 LLM 에이전트 서비스의 채팅 스트리밍을 맡으며 겪은 문제들을 정리했다.
> 에이전트 턴은 도구를 여러 번 부르며 몇 분씩 걸리기도 한다. 짧은 챗봇 응답에서는 안 보이던 문제가 여기서 나왔다.

## 1. 구조

```
브라우저 ──SSE── 웹 서버 ──구독── 에이전트 세션 서버 ── 모델 provider
```

- 웹 서버는 세션 서버의 이벤트를 구독해서 브라우저로 SSE를 중계한다.
- 긴 턴은 여러 **세그먼트**로 나뉜다. 모델이 도구를 부르면 결과를 넣고 다시 이어서 생성하는데, 그때마다 구독을 새로 연다.
- 즉 한 턴 안에 "구독 열기 → 입력 보내기 → 스트림 받기"가 수십 번 반복될 수 있다.

![한 턴의 세그먼트](/images/posts/long-running-agent-streaming/turn-segments.svg)
*그림. 도구 결과를 넣고 이어서 생성할 때마다 새 세그먼트가 시작되고, 구독을 다시 연다.*

## 2. 텍스트가 끊겨 보이는 문제

provider에서 텍스트는 덩어리로, 일정하지 않은 간격으로 온다. 받은 대로 그리면 덜컥거려서, 버퍼(백로그)에 쌓아 두고 프레임마다 조금씩 꺼내 그렸다.

처음엔 프레임당 고정 글자 수를 꺼냈다. 그러자 **백로그가 적을 때** 다음 덩어리가 오기 전에 다 꺼내 버리고 멈췄다가, 다시 흐르는 stop-and-go가 보였다. 표출 속도가 도착 속도보다 빨랐기 때문이다.

```ts
// 표출 속도 = max(바닥 속도, 백로그를 목표 지연 안에 비우는 속도)
function charsToDrain(
  backlog: number, dtSec: number, carry: number,
  floorCps: number,     // 평균 도착 속도보다 낮게 잡는다
  targetLagSec: number, // 백로그가 크면 이 시간 안에 따라잡는다
) {
  const cps = Math.max(floorCps, backlog / targetLagSec);
  const budget = cps * dtSec + carry;
  const n = Math.min(backlog, Math.floor(budget));
  return { n, carry: budget - n };
}
```

- 핵심은 **바닥 속도를 평균 도착 속도보다 낮게** 잡는 것이다. 백로그가 적으면 자연히 느려져 바닥나지 않는다.
- 프레임 수가 아니라 **경과 시간(dt)** 기준으로 계산한다. 프레임 기준이면 고주사율 화면에서 두 배 빨리 흘러 더 끊겼다.
- 1글자 미만 남은 예산은 다음 프레임으로 이월하고, 유휴 상태에 들어가면 초기화해서 몰아 쓰기를 막았다.

![도착 속도와 표출 속도](/images/posts/long-running-agent-streaming/text-pacing.svg)
*그림. 고정 속도로 꺼내면 백로그가 바닥날 때마다 멈추고, 바닥 속도와 백로그 비례 속도 중 큰 값으로 꺼내면 끊기지 않고 흐른다.*

## 3. 화면이 스트림을 놓치는 문제

스트리밍 중에 다른 탭으로 갔다 돌아오면 질문과 응답이 사라졌다. 스트림은 살아 있었지만 이벤트가 **시작 시점의 컴포넌트 콜백**으로만 흘러서, 컴포넌트가 내려가면 다 버려졌다.

- 스트림을 컴포넌트 밖 전역 저장소에 두고, 받은 이벤트를 **스냅샷**으로 누적한다.
- 리스너는 교체 가능한 슬롯으로 둔다. 다시 마운트되면 붙으면서 스냅샷을 받아 화면을 채운다(마지막에 붙은 리스너가 이긴다).
- 새로고침처럼 클라이언트가 사라지는 경우를 위해, 서버의 생성은 클라이언트 연결과 분리했다. 연결이 끊겨도 턴은 끝까지 돌고 저장된다.

그래도 "답은 저장됐는데 화면은 로딩에 멈춘" 제보가 왔다. 로그상 스트림은 정상 완료됐는데, 그 화면 인스턴스가 완료 이벤트를 받지 못한 것이다. 리스너가 떨어진 정확한 경로는 끝내 재현하지 못했다.

그래서 원인 경로와 무관하게 되살리는 장치를 넣었다.

- 로딩 중인 화면을 주기적으로, 그리고 탭 복귀 때 확인한다.
- 스트림이 돌고 있는데 아무도 안 받고 있으면 다시 붙는다.
- 스트림이 끝났는데 **이 리스너는 종료 이벤트를 못 받았다면**, 서버에 저장된 대화를 조회해서 턴이 끝났으면 그 저장본으로 정상 완료 경로를 태운다.

원인을 다 모를 때는, 최종 상태가 저장되는 곳(서버)을 진실로 두고 화면을 거기에 맞추는 복구 경로가 유용했다.

## 4. 내가 누르지 않은 "취소"

사용자가 누르지 않았는데 "요청이 취소됐어요"가 떴다.

원인은 웹 서버가 세션 서버 구독에 건 **연결 상한**이었다. 상한에 걸리면 `AbortController`로 끊었고, 그 `AbortError`가 그대로 올라가 "사용자 취소"로 분류됐다. 디버그 정보의 발생 레이어도 클라이언트로 찍혀서 조사를 더 헷갈리게 했다.

```ts
function classifyAbort(err: unknown, userSignal: AbortSignal) {
  if (userSignal.aborted) return "USER_CANCELLED";
  if (isAbortOrTimeout(err)) return "UPSTREAM_TEMPORARY"; // 서버 내부에서 끊음
  return "UNKNOWN";
}
```

- **사용자 취소는 사용자의 signal이 abort됐을 때만**이다. 그 외의 abort/timeout은 "내부 호출이 끊김"으로 분류하고 "일시 오류, 다시 시도"로 보여 준다.
- 서버가 만든 오류는 레이어도 서버로 표기한다.
- 스트림 이벤트와 저장되는 오류 마커가 같은 분류 함수를 쓰게 했다. 둘이 다르면 새로고침 전후로 다른 오류가 보인다.

## 5. 도구 결과를 스트림 이벤트로

일부 도구는 세션 서버가 직접 실행한다. 이 도구들의 기록 형식이 바뀌면서, 서버 도구 호출이 클라이언트 도구 호출과 **같은 모양**으로 오게 됐다.

그런데 웹 서버는 "이 턴에 등록되지 않은 이름의 도구 호출 = 실패"로 바로 기록하고 있었다. 그대로 두면 서버 도구가 전부 실패 카드로 남는다.

- 모르는 이름의 호출은 바로 기록하지 않고 **뒤따르는 신호로 확정**한다.
  - 결과 이벤트가 오면: 서버 도구다. 결과로 성공·실패를 기록한다.
  - "클라이언트가 실행해야 할 목록"에 들어 있으면: 진짜 없는 도구다. 실패로 기록한다.
  - 둘 다 없이 요청이 끝나면: 구버전 서버의 서버 도구다. 저장된 기록에서 결과를 읽는다.
- 클라이언트가 먼저 배포돼야 하는 순서라, **신구 형식을 모두 받는** 쪽으로 만들었다.
- "없는 도구" 경고 로그도 호출 시점이 아니라 확정 시점으로 옮겼다. 호출 시점에는 아직 모른다.

## 6. 긴 턴이 마지막에 끊기는 문제

몇 분 일한 턴이 끝에서 "일시적인 서버 오류"로 끊긴다는 제보가 몇 건 왔다. 원인은 달랐지만 구조는 같았다. **세그먼트마다 다시 하는 호출 하나가 상한을 넘기면 턴 전체가 실패**했다.

- 한 건은 세그먼트 구독의 연결이 늦었다. 앞 세그먼트들은 금방 연결됐다.
  → 연결 상한에 걸리면 **한 번 더 구독**한다. 입력을 보내기 전이라 같은 입력이 두 번 실행되지 않는다.
- 다른 건은 도구 결과를 넘기기 전에 하는 권한 재확인 조회가 느렸다.
  → 도구 결과 세그먼트에서 재확인이 **조회 장애(타임아웃, 연결 실패, 5xx)로만** 실패하면 같은 턴 앞 세그먼트의 확인을 쓴다. 권한 거절은 그대로 실패시킨다. 세션 서버가 세그먼트마다 다시 검사하므로 우회가 아니다.
- 도구나 모델이 오래 조용한 구간에는 SSE에 주기적으로 heartbeat 주석을 보내 중간 프록시가 연결을 끊지 않게 했다.

턴이 길어질수록 "한 번쯤 느린 호출"은 확률이 아니라 확정이 된다. 반복되는 호출마다 무엇이 재시도해도 안전한지 따져야 했다.

## 7. 스트림 중간에 끊긴 provider 오류

모델 provider가 스트림을 연 뒤(HTTP 200) 도중에 오류를 보내면, **HTTP 상태 코드가 없다.** 분류 로직은 상태 코드를 기준으로 짜여 있어서 이 오류는 마지막 fallback인 "요청 오류(재시도 불가)"로 떨어졌고, 사용자는 원인 모를 내부 오류를 봤다.

- 상태 없는 provider 오류는, 더 구체적인 분류(콘텐츠 정책, rate limit, 문맥 초과 등)에 안 걸리면 **provider 일시 오류(재시도 가능)**로 분류한다. 요청 거절을 명시한 오류는 그대로 둔다.
- 서버에서 **딱 한 번** 자동 재시도한다. 조건은 아직 아무 출력도 내보내지 않았을 때다.

| 위험 | 판단 |
|---|---|
| 중복 출력 | 텍스트를 하나라도 내보냈으면 재시도하지 않는다 |
| 중복 도구 실행 | 도구 호출은 스트림이 끝날 때까지 버퍼링되므로 실패한 시도의 호출은 실행되지 않는다 |
| 중복 과금 | 사용량은 최종 결과에만 실리므로 실패한 시도는 사용자 사용량에 잡히지 않는다 |
| 지연 | 1회만, 전체 deadline 안에서 |

- rate limit이나 타임아웃은 즉시 다시 불러도 나아질 가능성이 낮아 재시도하지 않고, 대신 오류 이벤트에 `retryable: true`를 실어 클라이언트가 판단하게 했다.

## 8. 정리

- 스트리밍 UI는 "도착 속도"와 "표출 속도"를 분리해서 생각해야 한다.
- 화면 상태는 스트림이 아니라 **저장된 상태**를 진실로 두고 복구할 수 있어야 한다.
- abort는 누가 했는지로 분류한다. 사용자 취소와 서버 내부 abort를 섞으면 조사도, 안내도 틀린다.
- 긴 턴에서는 반복되는 모든 호출이 실패 지점이다. 재시도는 "아직 부작용이 없을 때"만 안전하다.
