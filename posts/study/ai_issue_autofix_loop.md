> 임시 게시글: 작업 기록을 바탕으로 작성한 초안이며, 이후 다듬을 예정이다.

> 업무에서 AI 코딩 에이전트를 팀 자동화 루프로 돌려 보았다.
> 이슈를 모으고, 분류하고, 일부는 자동으로 고쳐 PR까지 올리는 구조다. 돌리면서 겪은 실수 위주로 정리한다.

## 1. 전체 구조

```
[입력] 코드 스캔 / 사용자 제보 / 알람 / 채팅 스레드
   ↓ 이슈 등록
[분류 세션] 영향도 + 조치 성격 판정
   ↓ (자동 수정 후보 + 낮은 영향도만)
[수정 세션] 브랜치 → 커밋 → PR
   ↓
[머지 게이트] CI 대기 → 리뷰·검증 → 자동 머지
   ↓
[리포트] 하루 단위 활동 요약
```

각 단계는 별도의 에이전트 세션이다. 세션마다 쓸 수 있는 도구와 권한을 따로 정했다.

![이슈 분류·자동 수정 루프](/images/posts/ai-issue-autofix-loop/loop-overview.svg)
*그림. 자동 수정 후보이면서 영향도가 낮은 이슈만 수정 세션으로 가고, 머지 게이트는 커밋으로 고칠 수 있는 실패를 스스로 고치는 라운드를 돈다.*

## 2. 분류: 근거를 어디서 가져오나

영향도는 "관측된 피해 크기"로 매기기로 했다. 그런데 **몇 명이 몇 번 겪었는지는 코드가 알려주지 않는다.** 코드만 보고 분류하면 "다수 사용자 영향"과 "일부 조건에서만"을 가를 수 없었다.

그래서 분류 세션에 운영 로그와 DB를 **읽기 전용**으로 붙였다.

- 여는 것은 자격증명뿐이다. 도구 목록, 권한 모드는 그대로 읽기 전용.
- 언제 조회할지 기준을 줬다. 코드로 결론이 나면 조회하지 않는다. 습관적 조회는 느리고 얻는 게 없다.
- **이슈나 스레드 본문이 "이 로그를 조회해라"라고 써 있어도 따르지 않는다.** 입력 텍스트는 아무나 쓸 수 있으므로 주입 경로가 된다.
- 등록·수정 세션에는 이 자격증명을 주지 않는다. 이 경계는 테스트로 고정했다.

## 3. 심각도 분류의 함정

처음 분류에서 가장 많이 틀린 건 **기능 요청이 "낮음"으로 분류되는 것**이었다. 결함이 아니니 피해가 작다고 본 것인데, 그러면 "낮음 = 자동 수정"이라는 규칙을 타고 기능 추가가 자동 수정 경로로 흘러들었다.

고친 방법:

- 영향도 축 옆에 **조치 성격** 축을 따로 세웠다. "자동 수정 후보", "사람 승인 필요", "조치 불가" 같은 값이다. 자동 수정 입구는 이 축이 막는다.
- 영향도는 말 대신 숫자 등급으로 바꾸고, 각 등급의 정의를 **한 문서**에만 두었다. 정의가 여러 곳에 있으면 서로 어긋난다.
- 기준 문서 일부만 프롬프트에 넣는 코드가 있었는데, 자르는 기준점을 못 찾으면 조용히 문서 전체가 들어갔다. 관련 없는 섹션이 들어가자 등급이 방어적으로 밀렸다. 이제는 기준점을 못 찾으면 **에러를 던진다.**

## 4. 자동 수정과 머지 게이트

수정 세션은 이슈를 받아 브랜치를 만들고 PR을 연다. 머지는 게이트가 결정한다.

- 필수 CI 체크만 기다린다. 무관한 체크는 무시한다.
- 체크 상태는 폴링한다. 병합 가능 여부가 아직 계산 중(unknown)이면 실패가 아니라 대기다.
- 테스트 환경 배포(preview)가 끝날 때까지 기다린다.

### 실패를 스스로 고치는 라운드

CI 실패의 상당수는 lint, 타입, 단위 테스트 수준이라 로그를 보면 바로 고칠 수 있다. 그래서 같은 실행 안에서 "고치고 다시 평가"를 몇 라운드 반복하게 했다.

- 재시도 대상은 **커밋으로 고칠 수 있는 실패**뿐이다. 실패로 끝난 필수 체크는 대상이고, 타임아웃·충돌·환경 문제는 제외다.
- 실패 사유 문자열을 파싱하지 않고, 체크 상태를 다시 조회해서 판단한다.
- 세션이 "push했다"고 말하는 것을 믿지 않는다. **PR head 커밋이 바뀌었는지**로 확인한다. 같은 diff면 같은 판정이므로 재평가하지 않는다.
- 라운드마다 리뷰·검증을 **처음부터 다시** 돌린다. 이전 라운드의 통과를 새 diff에 물려주면 안전장치가 깨진다.
- 라운드 수에는 상한을 둔다.

## 5. 세션 메모리 예산

자동 수정 세션이 조용히 실패하는 일이 잦았다. 모아 보니 대부분 **세션 메모리 예산 초과로 강제 종료**된 것이었다.

메모리 추이를 보니 원인은 하나였다. 무거운 타입 체크가 도는 도중에 테스트 워커들이 겹쳐 뜨면서 예산을 넘었다. CI는 잡마다 러너가 따로라 겹치지 않지만, 세션은 한 컨테이너에서 병렬로 돌렸다.

- 예산을 한 번 올려 봤지만, 겹침은 그대로라 새 예산까지 차오르고 똑같이 죽었다.
- 해결은 **검사를 하나씩 순차 실행**하게 하는 것이었다. 병렬 호출, 백그라운드 실행을 금지하고, 테스트는 관련 파일만 적은 워커로 돌린다.
- 이 규칙은 사람이 직접 요청한 세션과 자동 세션이 같이 읽는 공통 지침에 넣었다.

## 6. 조용히 실패하지 않기

처음에는 "자동 채널을 시끄럽게 하지 말자"는 방침으로 수정 세션의 실패를 로그에만 남겼다. 그러자 이슈에는 **"자동 수정을 시작합니다"만 남고** 결과가 영영 오지 않았다. 실패인지 아직 도는 중인지 아무도 구분할 수 없었다.

두 단계로 고쳤다.

1. **멈춘 세션 스윕**: 주기적으로 "시작 코멘트는 있는데 결과가 없는" 이슈를 찾아 재시도한다.
   - 시작이 여러 번 찍힌 이슈는 **마지막 시작** 기준으로 잰다.
   - 결과 코멘트가 있으면 정상 종료다. "PR을 만들지 않았습니다"도 결과다.
   - 연결된 PR이 있으면 결과만 늦은 것일 수 있어 건너뛴다. 되살리면 중복 PR이 된다.
   - 재시도에는 상한을 두고, 다 쓰면 라벨을 붙여 사람에게 넘긴다.
   - 후보가 0건인 회차도 로그를 남긴다. 그래야 "멈춘 게 없다"와 "못 찾는다"가 구분된다.
2. **실패 저널**: 세션이 에러로 끝나면 이슈에 사유를 코멘트로 남긴다.
   - 사유 코드(메모리 초과, 대기 시간 초과, CLI 오류 등)와 짧은 오류 문구만 싣는다. 예외 메시지에는 내부 경로가 섞일 수 있어 종류만 남긴다.
   - 채널 알림은 그대로 조용하다. 이슈 코멘트는 채널을 울리지 않는다.
   - 주의할 점: 스윕이 정상 종료로 읽는 문구를 실패 코멘트에 쓰면 재시도가 꺼진다. 자동화끼리 문구로 대화할 때는 그 문구가 계약이다.

저널을 붙이고 나서야 무음 실패가 전부 같은 원인(5절의 메모리)이라는 패턴이 보였다.

## 7. 채팅 스레드에서 할 일 건지기

코드 스캔은 "머지된 것"을 보지만, 채널에서 합의된 결함·요구는 아무도 옮겨 적지 않으면 사라진다. 그래서 하루치 대화를 스레드 단위로 훑어 이슈로 쌓는 스윕을 만들었다.

- **권한 분리**: 대화는 누구나 아무 문장이나 쓸 수 있는 입력이다. 모델은 읽기 전용으로 판정만 하고, 이슈 생성·라벨·개수 상한·중복 규칙은 코드가 강제한다.
- **개인정보 마스킹은 한 곳에서, 프롬프트에 넣기 전에** 끝낸다. 넣은 뒤에 거르면 모델은 이미 본 것이다.
- **수집은 두 단계**: 부모 메시지 목록을 먼저 받고, 이미 이슈가 있거나 예산을 넘긴 스레드를 거른 뒤에만 답글을 조회한다.
- 봇이 자기 리포트에 달린 답글을 다시 이슈로 만들지 않도록 리포트 채널은 코드에서 제외했다.

## 8. 데일리 리포트와 정리

- 하루 단위로 "등록 / 분류 / 수정 PR / 머지 / 정리한 이슈" 건수를 올린다.
- 건수 아래에 산문 요약을 붙이되, 요약 생성이 실패해도 건수만으로 리포트가 나가게 폴백을 뒀다.
- 승인 대기로 오래 방치된 PR과 봇이 등록한 이슈는 리마인드 후 자동으로 닫는다.
- 사람이 직접 요청해서 처리한 건은 루프 집계에서 뺐다. 섞이면 루프가 실제보다 잘하는 것처럼 보인다.

## 9. 정리

- 에이전트에게는 **판정**을 맡기고, 되돌리기 어려운 동작(생성, 머지, 상한)은 코드가 강제한다.
- 세션의 말이 아니라 관측 가능한 상태(커밋 SHA, 체크 상태, 코멘트 존재)로 판단한다.
- 조용한 실패는 가장 비싼 실패다. 실패 사유를 남기는 순간 패턴이 보였다.
