> 임시 게시글: 작업 기록을 바탕으로 작성한 초안이며, 이후 다듬을 예정이다.

> 업무에서 AI 에이전트가 사용자의 입력 없이도 일을 시작하게 하는 기능을 만들었다.
> 정해진 시각에 도는 **예약 작업**과, 새 메일·새 파일이 들어오면 그 항목을 첨부해 대화를 여는 **이벤트 트리거**다.

## 1. 이벤트 트리거의 흐름

"지정한 메일함이나 폴더에 새 항목이 들어오면, 그 항목을 첨부해서 미리 정한 메시지로 새 에이전트 대화를 연다."

이미 "새 항목 감지 → 워크플로 실행" 기능이 있어서, 감지 경로(웹훅 수신, 중복 제거, 복구 스윕)는 그대로 공유하고 **실행 대상만 하나 추가**했다.

항목 하나의 처리(delivery)는 상태 머신으로 뒀다.

```
가져오기(항목 조회, 필터 재판정)
  → 올리기(첨부를 파일로 업로드)
  → 대화 시작(새 대화를 만들고 턴 시작)
  → 넘김 완료
```

- 턴을 시작하기 **전에** 만든 대화 id를 먼저 기록한다. 그래야 중간에 죽어도 어디까지 갔는지 안다.
- 작업 리스가 만료됐을 때, 업로드 단계였다면 다시 대기열에 넣는다. 턴 단계였다면 **자동 재시도하지 않는다.** 턴이 이미 시작됐는지 모르는 상태에서 다시 돌리면 같은 메일로 대화가 두 번 열린다.

## 2. 과거 항목을 되살리지 않는다

트리거는 만든 뒤에 새로 들어온 항목만 대상으로 했다(backfill 없음).

- 메일은 트리거를 켠 시각을 저장하고, **받은 시각이 그보다 이르거나 모르면** 건너뛴다. 메일함 연결을 다시 하거나 변경 이력 커서가 만료되면 메일함을 다시 훑게 되는데, 이때 지난 메일마다 무인 대화가 열리면 안 된다.
- 폴더는 반대로 파일 시각으로 거르지 않았다. 폴더는 다시 훑는 경로가 없고 "켠 뒤 관찰한 변경"만 들어온다. 오래된 파일을 폴더로 옮겨 넣은 경우가 빠지면 안 되기 때문이다.

같은 "과거 항목 거르기"라도 소스마다 재스캔이 일어나는 경로가 달라서 규칙이 달라졌다.

- 메일 첨부 하나가 거절되면(형식, 크기) **그 첨부만 빼고** 대화를 연다. 본문이나 폴더 파일 자체가 거절되면 실패시킨다.
- 실패한 항목은 화면에서 다시 시도할 수 있게 했다.

## 3. 폴링 간격

웹훅을 주지 않는 소스는 주기적으로 확인(폴링)한다. 간격은 반응성과 비용(호출 수, rate limit) 사이의 trade-off다.

실제로 써 보니 "메일을 보냈는데 한참 뒤에 시작한다"는 체감이 컸고, 간격을 한 번 줄였다. 사용자가 직접 결과를 기다리는 기능이라면 간격은 생각보다 짧아야 했다.

## 4. 발신자 매칭

처음엔 메일 트리거의 발신자를 주소 하나로만 정확히 비교했다. 팀 주소 여러 개나 도메인 전체를 받으려면 트리거를 여러 개 만들어야 했고, 만든 뒤에는 고칠 수도 없었다.

### 여러 주소와 와일드카드

- `*`는 위치 제한 없이 아무 글자와 맞는다. `*@partner.com`, `billing*@co.com`, `*`(모든 발신자).
- 목록 중 하나라도 맞으면 통과한다.
- 매칭은 사용자 입력을 정규식으로 바꾸지 않고 **glob 함수**로 직접 했다. `*a*a*a…` 같은 패턴에서 정규식 역추적이 폭증하는 것(ReDoS)을 피하려고.

```ts
// 사용자 패턴을 정규식으로 만들지 않는 단순 glob 매칭
function globMatch(pattern: string, text: string): boolean {
  let p = 0, t = 0, star = -1, mark = 0;
  while (t < text.length) {
    if (p < pattern.length && pattern[p] === text[t]) { p++; t++; }
    else if (p < pattern.length && pattern[p] === "*") { star = p++; mark = t; }
    else if (star !== -1) { p = star + 1; t = ++mark; }
    else return false;
  }
  while (p < pattern.length && pattern[p] === "*") p++;
  return p === pattern.length;
}
```

### 롤백해도 열리지 않게

새 형식(발신자 목록)을 저장하면서 **첫 패턴을 옛 단일 발신자 필드에도** 같이 적었다. 옛 코드로 롤백하면 옛 코드는 단일 필드만 읽는데, 비어 있으면 "필터 없음 = 모든 메일"로 열려 버린다. 첫 패턴이라도 적어 두면 좁게 닫힌다.

마이그레이션 없이 바꿀 때는 "롤백했을 때 넓어지는가, 좁아지는가"를 따져야 했다.

### @ 앞의 점

사용자가 `first.last@co.com`으로 등록했는데 실제 발신 주소는 `firstlast@co.com`이라 매칭이 안 됐다. 어떤 메일 서비스는 @ 앞의 점을 무시하고 같은 메일함으로 배달한다.

- 저장과 표시는 **입력한 그대로** 둔다. 사용자가 쓴 값이 바뀌어 보이면 혼란스럽다.
- **비교할 때만** @ 앞(local part)의 점을 빼고 비교한다. 도메인의 점은 그대로 둔다.
- 비교 시점에만 정규화하니 기존 트리거도 마이그레이션 없이 맞게 됐다.
- 점만 다른 패턴은 같은 메일과 맞으므로 **중복으로 본다.** 같은 메일함에 두 트리거가 있으면 메일 하나가 두 번 처리된다.

## 5. 승인 모드

에이전트가 외부에 쓰는 동작(파일 만들기, 메일 보내기 등)은 기본적으로 사용자 확인 카드를 띄운다. 그런데 무인 실행에서는 **아무도 카드를 누르지 않는다.** 실제로 트리거로 열린 턴이 폴더 생성 확인 카드에서 멈춰 있었다.

- "확인 없이 실행" 모드를 열었다. 단 사용자가 명시적으로 골라야 하고, 고르면 경고를 보여 준다. 메일·파일 속에 쓰인 지시도 확인 없이 실행될 수 있기 때문이다.
- 저장된 값이 없거나 모르는 값이면 **가장 보수적인 모드**로 읽는다.
- 유지한 안전장치: 메일 트리거는 발신자 지정 필수(모든 발신자는 `*`를 직접 써야 하고 경고를 띄운다), 첨부 파일명 중립화, 실행 시점에 끌 수 있는 kill switch.

## 6. 예약 작업 쪽에서 한 것

- **사용자당 개수 상한**을 두고, 모든 예약을 검색·필터·페이지로 보는 관리 화면을 따로 만들었다.
- 예약을 만든 화면의 언어와 타임존을 함께 저장한다. 결과 대화가 엉뚱한 언어로 오지 않게.
- 매일 도는 예약이 있으면 최근 대화 목록이 **같은 제목**으로 가득 차서 직접 나눈 대화가 밀려났다. 실행이 둘 이상인 예약은 한 줄로 묶고, 펼치면 **실행 시각**으로 구분해 보여 준다. 트리거가 연 대화도 같은 방식으로 묶었다.

## 7. PR preview 환경에서 생긴 문제들

PR마다 preview 환경을 띄우는데, 데이터베이스 스키마 변경이 없는 PR은 테스트 환경 DB를 **공유**한다. 이 구조에서 두 가지가 터졌다.

### 예약은 실패하는데 "지금 실행"은 성공

원인은 실행 코드가 아니라 **어느 컨테이너가 예약을 집었느냐**였다.

- 모든 컨테이너가 부팅 때 예약 스윕을 켠다. preview도 같은 DB의 예약을 집어서 **그 PR의 코드로** 실행했다.
- preview가 본 서비스보다 훨씬 많아서, 예약 대부분을 preview가 집고 있었다.
- 그중 스키마 변경 전에 빌드된 preview가 컬럼이 사라진 뒤로 집은 예약은 전부 실패했다.
- "지금 실행"은 요청을 받은 본 서비스에서 바로 돌아서 영향이 없었다.

해결: **공유 DB를 쓰는 preview에서만** 주기 스윕을 끈다. 격리 DB preview는 스케줄러를 시험할 수 있게 그대로 켠다.

### 트리거 이벤트가 preview로 오지 않음

웹훅 구독 URL이 프로젝트당 하나(테스트 환경)뿐이라, preview에서 트리거를 만들어도 이벤트는 테스트 환경으로 갔다. 머지 전에 트리거 PR을 검증할 방법이 없었다.

- 웹훅 중개 서비스가 지원하는 **인스턴스별 전달 URL 덮어쓰기**를 써서, preview가 켠 소스의 이벤트만 그 preview로 보낸다.
- 다른 트리거도 같은 소스를 쓰고 있으면 덮어쓰지 않는다. 테스트 환경 트리거의 이벤트를 PR 코드가 처리하면 안 된다.
- 본 서비스는 소스를 켤 때 걸려 있던 덮어쓰기를 지운다. 내려간 preview로 이벤트가 새지 않게.
- 공유 DB preview는 자기가 기록한 트리거의 delivery만 처리한다. 전에는 preview가 남의 delivery를 PR 코드로 집어갈 수 있었다.

## 8. 정리

- 무인 실행에서는 "이미 시작했는지 모르는 상태"가 가장 위험하다. 부작용 전에 기록하고, 부작용 단계는 자동 재시도하지 않는다.
- 사용자 입력은 저장·표시는 그대로, 비교할 때만 정규화한다.
- 롤백했을 때 필터가 넓어지는지 좁아지는지 따진다.
- 공유 자원(DB, 웹훅 URL)을 쓰는 preview는 백그라운드 작업이 남의 일을 집어가지 않게 막아야 한다.
