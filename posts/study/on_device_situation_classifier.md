> 임시 게시글: GitHub 기록을 바탕으로 작성한 초안이며, 이후 다듬을 예정이다.

> [Owl](https://github.com/wndgur2/owl) 타임라인 기록마다 "그때 어떤 상황이었나"를 붙이는 분류 모델 [owl_laya](https://github.com/wndgur2/owl_laya)를 설계했다.  
> 아직 코드는 없는 설계 초안 단계이고, 설계하면서 정한 내용과 이유를 정리했다.

## 1. 목표

Owl 타임라인은 지금 [시각 · 장소 · 텍스트]를 보여준다. 여기에 **상황**을 더해서, 하루를 돌아볼 때 "오전엔 강의, 점심엔 친구랑 수다, 오후엔 팀플 회의"처럼 한눈에 보이게 하는 게 목표다.

조건은 하나다. Owl의 원칙(PRD N8)대로 **모든 처리가 폰 안에서 끝나야 한다.** 서버나 외부 API로 보내는 경로는 없다.

## 2. 라벨 체계

| 라벨 | 한 줄 정의 | 대표 예 |
|---|---|---|
| 독백 | 듣는 상대 없이 혼자 말함 | 혼잣말, 음성 메모 |
| 일상 대화 | 2명 이상이 업무와 무관하게 주고받음 | 친구·가족과 수다, 식당 주문 |
| 강의 | 한 화자가 다수를 상대로 길게 설명 | 수업, 세미나, 유튜브 강의 청취 |
| 일 | 업무·과제 목적의 대화 | 회의, 페어 프로그래밍, 팀플 |
| 기타 | 사람 대화가 아니거나 판단 불가 | 미디어 소리, 소음 |
| 불확실 | 모델 확신이 임계값 미만 | 사용자가 확인 |

`기타`를 따로 둔 이유: 결정 모델은 정답이 선택지에 없어도 그중 하나를 자신 있게 고르는 경향이 있다. 음악·드라마 소리를 받아 줄 출구가 필요하다.

애매할 때는 우선순위로 정한다. 사람 대화가 아니면 `기타` → 혼자 말하면 `독백` → 한 사람이 다수에게 체계적으로 설명하면 `강의` → 나머지는 목적으로 `일` / `일상 대화`를 가른다. "혼자 하는 업무 중얼거림"이나 "회의 중 발표" 같은 경우는 제품 결정이라 라벨링 전에 확정하기로 남겨뒀다.

## 3. 파이프라인

```
목걸이 녹음 → (BLE) → 폰 STT → 타임라인 기록(간격 2분 이하 묶음)
  → 2분 윈도우 분할 → state 구성 → Laya 분류(INT8 ONNX)
  → temperature 보정 → 확신 ≥ 0.7 ? 스무딩·병합 : 사용자 확인
  → 교정 데이터 → 재보정·재학습
```

모델 호출은 이 흐름에서 **한 칸뿐**이다. 피처 계산, 임계값, 스무딩은 결정적인 코드로 처리해서 모델이 의미 판단에만 집중하게 했다.

### 입력 (state)

Owl v1에는 화자 구분이 없다. 그래서 입력은 **전사 텍스트 + STT 타임스탬프로 계산한 발화 통계 + 시각·장소**다.

| 필드 | 왜 넣나 |
|---|---|
| transcript | 의미 판단의 주 재료. 말투(존댓말 설명조, 반말 주고받기)가 큰 단서 |
| speech_ratio | 강의는 말이 쉼 없이 이어지고, 독백은 띄엄띄엄 |
| sentences_per_min, mean_sentence_sec | 강의는 긴 문장, 대화는 짧은 문장이 빠르게 오감 |
| long_pauses | 문장 사이 5초 이상 공백. 혼잣말의 특징 |
| time, place | 보조 단서 |

주의할 점도 적어뒀다.

- **독백 ↔ 대화 구분이 v1의 약점이다.** 화자 정보 없이는 "혼잣말"과 "상대 말이 작게 잡힌 대화"가 헷갈린다. 오디오 음량으로 착용자 발화 비율을 추정하는 실험을 v1.5로 계획했다.
- **메타 정보 과의존.** 모델이 "평일 오전 + 공학관 = 강의"를 외울 수 있다. 학습 때 time·place를 일정 확률로 지우고, 평가 때 메타 유무를 따로 재기로 했다.

## 4. 왜 Laya인가

### 결정 모델(System One model)

텍스트를 생성하지 않고, 개발자가 정한 선택지 중 하나를 **확률과 함께** 고르는 모델이다. 입력은 state와 타입이 정해진 질문(`choice`, `noul`, `score`)이고, 출력은 선택지별 확률이다. 토큰을 생성하지 않으니 출력 형식이 깨질 일이 없다.

### 후보 비교

| 모델 | 판단 |
|---|---|
| Jev | 가중치가 없고 API만 있음. 로컬 실행 불가라 N8 위반 → 탈락 |
| Kev-4B | 제로샷은 강하지만 4B 이상이라 폰 상시 탑재가 무겁고, 한국어가 측정된 적 없음 → 로컬 초벌 라벨러·참조 베이스라인으로 |
| Malkuth-4B | 한국어 중심이지만 비상업 라이선스 → 제외 |
| **Laya-multilingual (322M)** | 작고 빠름, Apache 2.0 → **채택** |

Owl의 질문은 "이 구간은 독백/대화/강의/일 중 무엇인가"로 거의 고정이다. 질문이 고정이면 제로샷 능력보다 **작은 크기와 튜닝 효율**이 중요하다.

다만 Laya는 제로샷 엔진이 아니라 "특화시키기 위한 베이스"라서 파인튜닝이 전제다. 또 영어 체크포인트는 한국어를 거의 못 읽고, 틀리면서도 확신을 높게 내는 사례가 모델 카드에 보고돼 있어서 반드시 `multilingual` 체크포인트를 쓴다.

## 5. Temperature 보정

### 배경

분류 모델이 "0.9 확신"이라고 했을 때 실제로 90% 맞아야 확률을 임계값에 쓸 수 있다. 이 어긋남을 재는 지표가 **ECE**(Expected Calibration Error)다.

**Temperature scaling**은 가장 단순한 보정법이다. logit을 하나의 값 T로 나눈 뒤 softmax를 취한다. T > 1이면 확률 분포가 평평해져 과신이 줄어든다. T는 val셋에서 NLL이 최소가 되도록 찾고, **가중치는 건드리지 않는다.** 그래서 argmax(예측 라벨)는 바뀌지 않고 확률만 바뀐다.

### 왜 필수인가

Laya 모델 카드에 따르면 출시된 체크포인트는 확신을 과하게 낸다. (질문 유형, 선택지 수)별로 temperature를 다시 맞추면 multilingual의 평균 ECE가 0.314에서 0.106으로 떨어진다고 보고됐다.

설계에서 정한 규칙은 이렇다.

- 보정은 반드시 **val셋**으로 하고, test셋은 마지막 평가에만 쓴다.
- 가중치를 바꾸지 않으므로, 사용자 교정이 쌓이면 **폰 안에서** temperature만 몇 초 만에 다시 맞출 수 있다.
- 체크포인트 · temperature 값 · 질문 스키마는 **한 버전 번들**로 묶는다. 하나만 바뀌어도 확률의 의미가 달라지기 때문이다.

## 6. 추론 정책

모델 출력을 그대로 쓰지 않고 세 단계를 거친다.

1. **임계값**: 보정된 최대 확률이 0.7(시작값) 이상이면 확정, 아니면 `불확실`로 두고 하루 돌아보기에서 사용자가 고른다.
2. **시간 스무딩**: 상황은 몇 분 단위로 지속되니 윈도우 하나가 튀는 건 대부분 오류다. v1은 히스테리시스(새 라벨이 연속 2개 윈도우에서 이겨야 바꿈), v2는 Viterbi(HMM에서 가장 그럴듯한 라벨 시퀀스를 DP로)를 계획했다.
3. **구간 병합**: 같은 라벨이 이어지는 윈도우를 합친다.

사용자가 라벨을 고치면 그 (state, 정답)이 새 학습 데이터가 된다. 확인 요청은 확신이 가장 낮은 윈도우부터 하루 몇 개로 제한한다. 매번 묻는 앱은 금방 꺼지기 때문이다.

## 7. 온디바이스 배포 (ONNX)

ONNX로 내보내 INT8로 양자화한 뒤 Android ONNX Runtime에서 돌리는 계획이다.

- 실시간일 필요가 없으므로 **STT가 끝난 뒤 배치로** 처리한다. Owl 앱의 `SyncWorker` → `TranscribeWorker` 뒤에 `ClassifyWorker`를 잇고, 충전 중·유휴 상태 제약을 건다.
- 모델 크기(322M 기준 추정): FP32 약 1.3GB, FP16 약 650MB, **INT8 약 330MB**(1차 목표).
- 최적화 포인트: mmBERT 어휘가 256k라 **임베딩 행렬만 전체의 약 60%** 다. 한국어에 실제로 나오는 토큰만 남기면 절반 이하로 줄 수 있다고 보고 v2 과제로 뒀다.
- 토크나이저는 학습 때와 같은 것이 폰에서도 돌아야 하고, 토큰 ID가 같은지 테스트로 고정하기로 했다.
- 양자화 후에는 FP32 대비 macro-F1 하락 1%p 이내를 게이트로 잡았다.

## 8. 프라이버시 원칙

Owl의 "내 기록은 밖으로 나가지 않는다"를 학습 단계까지 그대로 적용했다.

- 내 기록으로 만든 데이터, 체크포인트, ONNX 파일은 레포에 커밋하지 않는다(`.gitignore`로 막음).
- 내 기록은 Owl 앱의 내보내기로 PC에 꺼내서 **로컬에서만** 라벨링·학습한다. 외부 API, 클라우드 노트북, Hugging Face Hub에 올리지 않는다.
- 초벌 라벨도 로컬에서 도는 모델로만 받는다. 공개 코퍼스(AI-Hub 등)로 하는 실험만 어디서 돌려도 된다.
- 체크포인트는 내 대화에서 배운 모델이라 공개 Hub에 올리지 않는다.

## 9. 평가 계획

클래스가 불균형하므로 정확도 대신 **macro-F1**을 주 지표로, 확률을 임계값에 쓰므로 **ECE**와 **coverage**를 같이 보기로 했다. 같은 녹음에서 나온 인접 윈도우는 거의 중복이라, train/val/test는 **날짜 단위로** 나눈다. 랜덤으로 나누면 테스트 점수가 부풀려진다.

베이스라인은 규칙 몇 줄 / Laya 제로샷 / Kev-4B 참조값 세 가지다. 규칙만으로 충분하면 거기서 멈춰도 된다는 게이트도 뒀다.

## 10. 현재 상태

- 설계서와 모델 조사만 있고, 학습·평가·보정·ONNX 변환 스크립트는 예정이다.
- Owl PRD에는 아직 없는 기능이다. 진행하면 P2 「제안」으로 먼저 올려야 한다.
- Owl의 STT 엔진(whisper.cpp 또는 sherpa-onnx)이 정해져야 실제 기록으로 학습할 수 있다.
