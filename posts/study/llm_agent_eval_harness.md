> 임시 게시글: 작업 기록을 바탕으로 작성한 초안이며, 이후 다듬을 예정이다.

> 업무에서 LLM 에이전트 서비스를 만들며, 에이전트의 품질을 숫자로 확인하기 위해 평가(eval) 하니스를 만들었다.
> 그 과정에서 했던 설계 결정과 실수를 정리해 둔다.

## 1. 왜 필요했나

프롬프트 한 줄, 도구 설명 하나, 모델 하나를 바꿀 때마다 "좋아졌나?"를 감으로 판단하고 있었다.
몇 번 직접 대화해 보고 괜찮으면 배포했고, 며칠 뒤 다른 시나리오가 깨진 걸 사용자 제보로 알았다.

필요한 건 두 가지였다.

- 이미 한 번 터진 문제를 **회귀 케이스**로 고정해 두는 것
- 변경 전후를 **같은 기준**으로 비교할 수 있는 숫자

## 2. 블랙박스로 만든다

하니스는 앱 코드를 import하지 않는다. 브라우저가 쓰는 것과 같은 스트리밍 API로 대화를 보내고, 응답 이벤트와 최종 저장 결과만 보고 채점한다.

- 내부 구현(프롬프트 조립, 런타임 교체)이 바뀌어도 eval은 그대로 돈다.
- 실제로 런타임을 통째로 갈아끼울 때, 같은 코퍼스를 신구 런타임에 각각 돌려 비교하는 데 그대로 썼다.

단점은 느리고 비싸다는 것이다. 실제 LLM을 부르므로 케이스 수, 반복 횟수가 곧 비용이다.

## 3. 케이스 구조

케이스 하나는 "여러 턴의 사용자 입력 + 기대값"이다. YAML로 쓰고 스키마 검증을 거쳐 로드한다.

```yaml
id: summarize-attached-report
turns:
  - say: "첨부한 보고서를 세 줄로 요약해서 저장해줘"
    file: sample-report.pdf
    answer:
      language: ko
      mustNotInclude: ["죄송"]
expect:
  calledTool: save_note
  savedIncludes: ["요약"]
```

채점은 단계별 funnel로 했다. 예를 들어 `도구 선택 → 결과물 생성 → 저장 → 실제 실행`처럼 나누면, 어느 단계에서 깨졌는지가 바로 보인다. 최종 성공률 하나만 보면 "어디가 나빠졌는지"를 알 수 없었다.

여기에 직교하는 체크를 따로 뒀다.

- **턴별 reply 체크**: 답변 언어가 사용자 언어를 따라가는지, 특정 문구가 들어가거나 빠졌는지
- **negative 케이스**: 거절이 정답인 경우(너무 큰 입력 등). 처음엔 이걸 일반 케이스처럼 채점해서 "거절 = 실패"로 거꾸로 집계됐다. 별도 버킷으로 빼고 판정을 뒤집었다.
- 도달하지 못한 턴의 체크는 **실패**로 본다. 처음엔 건너뛰어서 false-green이 났다.

## 4. 시드 코퍼스

처음 코퍼스는 머릿속 시나리오가 아니라 다음에서 가져왔다.

- 실제로 났던 인시던트 재현
- QA에서 보고된 회귀
- 실제 사용 사례에 가까운 문서 fixture

그럴듯한 가상 케이스는 대부분 첫 실행부터 통과해서 아무것도 알려주지 않았다. 판별력은 실제 실패에서 나왔다.

## 5. 점수: 재시도 할인과 노이즈 밴드

에이전트는 첫 시도에서 틀리고 스스로 고쳐서 성공하기도 한다. 결과만 보면 성공이지만 사용자는 더 오래 기다렸다.
그래서 재시도한 만큼 점수를 깎았다.

```ts
// 첫 시도 성공 1점, 재시도마다 할인
function score(passed: boolean, retries: number, discount = 0.5) {
  if (!passed) return 0;
  return Math.pow(discount, retries);
}
```

또 같은 케이스도 돌릴 때마다 결과가 바뀐다. 한 번 뒤집힌 결과로 전체 지표가 흔들리지 않도록:

- 케이스마다 여러 번 반복 실행해 통과율을 낸다.
- 통과율에 신뢰구간(Wilson interval)을 붙이고, 구간이 넓은 케이스는 `flaky`로 표시한다.
- top-line 지표는 "첫 시도 성공률", "negative 통과율", "실행 단계 통과율"처럼 성격이 다른 것끼리 섞지 않았다.

## 6. 동시 실행과 라이브 결과

케이스가 늘자 직렬 실행은 너무 느렸다. 동시성 옵션을 두고 여러 케이스를 병렬로 돌렸다.
그 다음에 생긴 요구는 "돌아가는 중에도 결과를 보고 싶다"였다.

- 케이스가 끝날 때마다 결과를 **증분 저장**한다. run이 끝날 때 한 번에 쓰면, 중간에 죽었을 때 다 날아간다.
- 진행 상황은 SSE로 웹 화면에 흘린다. 여러 사람이 동시에 run을 돌려도 각자 보이도록 사용자 단위로 스트림을 나눴다.
- 완료된 run의 상세는 바뀌지 않으므로 브라우저에서 캐시했다.

### 중단과 이어하기

개발 서버가 메모리 한계로 재시작되면 run 전체가 미완료로 남았다. 두 가지를 했다.

1. run 시작 시 실행 계획(케이스 목록, 반복 수 등)을 저장해 두고, 이미 끝난 `케이스#회차`는 건너뛰고 나머지만 이어서 돌린다.
2. 애초에 덜 죽도록, 저장이 끝난 케이스의 전체 대화 기록은 메모리에서 버린다. 기록의 원본은 DB에 있다.

## 7. 인프라 실패는 실패가 아니다

반복 실행을 하다 보면 일부는 서버 재시작, 연결 끊김 같은 **인프라 문제**로 중단된다.
이걸 에이전트 실패로 세면 지표가 인프라 상태를 측정하게 된다.

- 중단 원인을 구분해서 인프라 실패는 채점에서 빼고 별도로 표시했다.
- 이어하기 시 인프라 실패 케이스는 **다시 실행**한다.
- 반대로 진짜 실패를 인프라 탓으로 숨기지 않도록, 분류 기준은 좁게 잡았다.

## 8. 케이스를 찾는 자동 루틴

코퍼스를 사람이 늘리는 속도는 느렸다. 그래서 정기적으로 도는 루틴을 만들었다.

1. 사용자 피드백·대화 채널에서 아직 코퍼스에 없는 시나리오를 찾는다.
2. 케이스 초안을 쓰고, 테스트 환경에서 반복 실행한다.
3. 결과와 함께 리뷰용 PR을 올리고 리포트를 남긴다.

정한 규칙:

- **전부 통과하는 신규 케이스는 버린다.** 지금 실패를 드러내는(red) 케이스가 가장 가치 있다.
- 기대값이 맞는지는 사람이 리뷰한다. 루틴이 쓴 기대값이 너무 느슨해서 무엇을 해도 통과하는 구멍이 실제로 있었다.
- 발굴 전에 최신 기준 브랜치를 받아 중복을 확인한다. 첫 시범 실행에서 찾은 red 케이스가 같은 날 다른 사람이 추가한 케이스와 거의 같았다.
- 루틴은 전용 작업 공간에서 돌리고, 테스트 서버가 버티도록 동시성을 낮게 잡았다.

## 9. 리포트

리포트는 읽히는 형태여야 했다.

- 맨 위에 회귀 검사 결과(통과율, 바뀐 케이스), 그 아래 신규 발굴 케이스
- 본문은 통계만, 케이스별 상세는 스레드 댓글로 분리
- 장식 이모지와 구분선은 뺐다. 케이스당 한 줄.
- run 전체를 JSON으로 내보내고 다른 환경에서 가져올 수 있게 해서, 로컬에서 돌린 결과를 공유 화면에 올릴 수 있게 했다.

## 10. 정리

- eval은 "얼마나 많이 도느냐"보다 **얼마나 유효한 케이스를 갖고 있느냐**가 본질이다.
- 단계별 funnel, 재시도 할인, 반복 + 신뢰구간은 숫자를 믿을 수 있게 만드는 최소한의 장치였다.
- 인프라 실패와 진짜 실패를 섞지 않는 것, 중간에 죽어도 결과가 남는 것이 생각보다 중요했다.
